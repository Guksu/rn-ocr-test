# 설계: RN 웹뷰 셸 앱 기술 검증 (rn-ocr-test)

| 항목 | 내용 |
|------|------|
| 최종 갱신 | 2026-08-29 |
| 상태 | 승인됨 (2026-08-29) |
| 참여 | 사용자(FE 담당) · Claude |

## 1. 목표와 완료 기준

React Native 웹뷰 셸 앱에서 네 가지 네이티브 기능(푸시 · OCR · 소셜 로그인 · 로그인 영속화)이
실제로 동작하는지 검증한다. 그중 **상품 성분표를 온디바이스 OCR로 읽어낼 수 있는가**가
가장 불확실하고 다른 결정을 좌우하므로 최우선으로 검증한다.

**완료 기준**

1. 네 기능이 실기기(iOS · Android)에서 동작한다.
2. 온디바이스 OCR의 성분표 인식 정확도를 **완전일치율 · 근사일치율** 수치로 제시한다.
3. 팀원 핸드폰(iOS · Android)에 설치해 실행·테스트할 수 있다.

## 2. 범위

**포함:**

- 웹뷰 셸 + 웹↔네이티브 브릿지
- 온디바이스 OCR 검증 (버리는 검증 코드)
- 소셜 로그인 3종(카카오 · 애플 · 구글), 푸시, 보안 저장소
- EAS 빌드 및 실기기 배포

**제외:**

- **서버 · 백엔드 전 영역** — 서버 LLM 비용 산정, LLM 모델 선택, 서버 OCR API 형태 등은 논의하지 않는다.
  그 결과 OCR 검증의 산출물은 "LLM 통과 후 정확도"가 아니라 **온디바이스 OCR 원본 정확도 데이터**이고,
  채택 여부 판정은 그 데이터를 팀이 들고 한다.
- 스토어 심사 준비물(개인정보처리방침 · 심사용 문구 · 스토어 등록) — 실제 제품 레포에서 수행
- 웹 서비스 자체 — 사용자가 직접 만들되 이 검증 이후로 미룸
- 실제 제품 코드 — 이 레포는 검증용이고 제품은 사내 비공개 레포에서 새로 시작

## 3. 시스템 구조

### 앱 구조 — 웹뷰 셸

화면은 전부 웹이 담당하고, RN은 웹이 할 수 없는 것만 브릿지로 제공한다.
웹은 후순위라 검증 단계에서는 웹 없이 진행한다.

```
┌──────────────────────────────────────┐
│  RN 앱 (껍데기)                       │
│  ┌────────────────────────────────┐  │
│  │  WebView = 웹 서비스 전체       │  │
│  └──────────────▲─────────────────┘  │
│              브릿지                    │
│  ┌──────────────▼─────────────────┐  │
│  │  푸시 · 카메라 · 소셜로그인      │  │
│  │  · 보안 저장소                  │  │
│  └────────────────────────────────┘  │
└──────────────────────────────────────┘
```

### 용어

- **브릿지**: 웹 페이지와 네이티브 코드가 주고받는 유일한 통신 통로. 앱이 웹에 `window.AppBridge`를 주입한다.
- **CNG (Continuous Native Generation)**: `ios/` `android/` 폴더를 커밋하지 않고 설정에서 매번 생성하는 Expo 방식.
- **개발 빌드(development build)**: 이 프로젝트 전용으로 빌드한 앱. Expo Go로는 카카오 로그인·푸시가 동작하지 않아 필수다.
- **완전일치율**: 정답 성분 중 글자까지 정확히 인식된 비율.
- **근사일치율**: 오타 수준(편집거리 2 이내)까지 인정한 비율. 완전일치율과의 격차가 "후처리로 복구 가능한 여지"를 뜻한다.
- **ocr-lab**: 검증 전용 코드의 위치. 1회용이며 제품 코드와 섞지 않고 검증 종료 후 폐기한다.

### 브릿지 규약

`src/bridge/protocol.ts`가 정본이며 웹 레포와 항상 동일하게 유지한다.
웹 개발자용 사용법은 `docs/bridge.md`.

### OCR 검증 설계

**샘플 3세트** — 섞지 않고 각각 점수를 낸다. 세트 간 격차 자체가 정보다.

| 세트 | 성격 | 검증 방식 |
|------|------|----------|
| 제조사 상세컷 | 평면 · 고조도 · 정면 (쉬움) | 배치 모드 (숫자) |
| 유저 업로드 (구글 · 네이버) | 실사용 분포에 가장 근접 | 배치 모드 (숫자) |
| 본인 촬영 20~30장 | 조건을 통제해 원인 규명 | 관찰 모드 (눈으로) |

**측정 조건 축**: 표면(평면/곡면) × 재질(무광/유광) × 조명(밝음/매장/그림자) × 글씨크기(대/소)

**지표**: 완전일치율, 근사일치율, 처리시간, 완전실패율, 라인 검출 수

**검증 앱의 두 모드** — ML Kit이 시뮬레이터에서 동작하지 않으므로 **둘 다 실기기에서 실행**한다.

- **배치 모드**: 이미지 여러 장을 순차 OCR하고, 정답을 입력하면 자동 채점해 집계를 낸다.
- **관찰 모드**: 이미지와 추출 결과를 나란히 놓고 사람이 즉시 눈으로 확인한다.

### 알려진 제약과 대응

| 제약 | 대응 |
|------|------|
| ML Kit은 Apple Silicon iOS 시뮬레이터에서 빌드 불가 (arm64 슬라이스 없음) | 실기기로 개발 |
| Android는 4MP 초과 이미지를 다운샘플하지 않고 throw | OCR 전 리사이즈 필수. iOS만 테스트하면 못 잡는다 |
| ML Kit은 문자당 최소 16×16px 요구 — 4MP 상한과 충돌 | **축소 전에 크롭**하면 픽셀 밀도가 유지된다. 부족하면 분할 OCR 후 좌표 병합 |
| OCR 라이브러리가 사실상 1인 메인테이너 | OCR 호출을 어댑터 뒤에 격리해 교체 가능하게 유지 |
| 테스트 이미지의 저작권 | **git 커밋 금지** (타사 제품 패키지 · 타인 촬영물) |

## 4. 실행 방식과 역할

직접 실행. 사용자가 앱·웹 프론트엔드를 단독 담당하므로 브릿지 규약을 한 손에서 관리한다
(향후 웹 착수 시 `protocol.ts`를 사내 패키지나 서브모듈로 공유하는 방안 검토).

**진행 순서**

1. OCR 검증 (최우선 — 불확실성 최대)
2. 이후 로그인 · 푸시 · 영속화 (순서는 검증 결과를 보고 결정)

## 5. 안전장치와 권한

- **레포는 비공개 유지.** 테스트 이미지 저작권, 소셜 로그인 키, 미출시 서비스의 기능 구성이 노출된다.
- 테스트 이미지와 `.env`는 커밋하지 않는다. `EXPO_PUBLIC_` 접두사 값은 앱 번들에 그대로 들어가므로 비밀값을 넣지 않는다.
- 검증 코드는 `ocr-lab` 이름으로 격리하고 제품 코드와 섞지 않는다.
- **배포**: Android는 EAS APK 링크, iOS는 TestFlight 외부 테스터 공개 링크(팀원을 계정에 초대하지 않아도 됨. 첫 빌드만 베타 심사 약 24시간).
- 계정: 개인 Apple Developer 계정 = 이 검증 / 법인 계정 = 실제 제품.
