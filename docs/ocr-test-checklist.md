# OCR 테스트 확인 목록

측정의 목적은 "잘 되나?"가 아니라 **"어디서, 왜 깨지나"** 를 알아내는 것이다.
잘 나온 사진만 모으면 실험이 무의미해진다.

## 1. 합성 배치 (자동 12장) — 한 번만 돌리면 됨

- [ ] **크기 스윕에서 급락 지점** — 한글 11 / 15 / 19 / 23 / 29 / 38px 중
      완전일치율이 무너지는 구간이 어디인가. **이 숫자가 촬영 가이드의 근거**가 된다.
      (ML Kit 문서의 "문자당 16px"이 한글에도 맞는지 여기서 확인된다)
- [ ] **조건 스윕 순위** — 저대비 / 기울임 / 블러 / 노이즈 / 복합 중 무엇이 가장 치명적인가.
      나중에 실사가 실패했을 때 원인을 짚는 기준표가 된다.
- [ ] **12MP 샘플** — 카드에 `축소됨 ⚠️` 이 뜨는가.
      → 뜨면 4MP 대응 정상. `4 MP` 에러가 뜨면 대응 실패이니 바로 알릴 것.
- [ ] **처리 시간** — 글자가 커질수록 느려지는가, 12MP 는 몇 ms 인가.

## 2. 관찰 모드 (실사) — 사진마다 기록

- [ ] 촬영 조건 4축: **표면**(평면/곡면) · **재질**(무광/유광) · **조명**(밝음/매장/그림자) · **글씨크기**
- [ ] `원본 해상도` 인가 `축소됨 ⚠️` 인가
- [ ] **검출 라인 수 vs 실제 줄 수** — 통째로 사라진 줄이 있는가
- [ ] **줄 순서가 맞는가** — 좌표 재정렬이 동작하는지 보는 지표.
      뒤죽박죽이면 성분 경계가 깨져서 정확도와 무관하게 못 쓴다.
- [ ] 성분 몇 개 중 몇 개를 맞췄는가
- [ ] 틀린 것이 **오타 수준**인가 **완전 실패**인가

## 3. 실패 패턴 — 가장 값진 관찰

숫자보다 이쪽이 다음 작업을 정한다. 반복되는 패턴이 보이면 기록할 것.

- [ ] 특정 자모가 반복해서 틀리는가 (ㅐ/ㅔ, ㅁ/ㅂ, 받침 유실)
- [ ] **숫자·기호가 섞인 곳**에서 깨지는가 — `1,2-헥산다이올`, `폴리글리세릴-10라우레이트`
- [ ] **영문 혼재 구간** — `EDTA-2Na`, `PEG-100`
- [ ] 줄 끝이 잘리는가 (블록 경계 문제)
- [ ] 곡면이면 **가장자리부터** 깨지는가 (중앙은 멀쩡한지)
- [ ] 반사 구간이 통째로 날아가는가

## 4. 즉시 알려야 할 신호 (내가 고쳐야 하는 것)

- [ ] 에러 메시지 (문구 그대로)
- [ ] `4 MP` 관련 에러 → 리사이즈 대응 실패
- [ ] 앱 크래시 · 멈춤
- [ ] 라인 순서가 뒤죽박죽
- [ ] confidence 가 전부 표시되지 않음 (안드로이드는 값이 나와야 정상)
- [ ] 처리 시간 5초 초과

## 5. 실험 위생

- **잘 나온 사진만 고르지 말 것.** 어려운 조건이 데이터의 핵심이다.
- **한 번에 한 변수만 바꿀 것.** 거리와 조명을 같이 바꾸면 원인을 못 가른다.
- 결과는 `배치 모드 → 결과 내보내기(JSON)` 로 회수할 수 있다.

### ★ 가장 값진 실험 하나

**같은 성분표를 거리만 바꿔가며 3~4장** 찍는다 (아주 가까이 → 멀리).
다른 조건이 전부 같으므로 **실사에서도 "몇 px부터 깨지는가"를 잴 수 있고**,
합성 결과와 대조하면 "합성이 실사를 얼마나 잘 예측하는가"까지 나온다.
그 격차가 작으면 앞으로 합성만으로 빠르게 반복할 수 있다.
